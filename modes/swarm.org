* Swarm Execution

Swarm is the default execution style for a single, self-contained piece of work
(a feature, fix, or refactor that lives in one worktree). The orchestrator
decomposes the work into parallel units, delegates them to executors, and gates
the result through the fan-out review engine. Epic execution (multi-worktree,
one PR per component) is used instead when the architect finds independent
multi-component scope.

** Core Principles

1. *Orchestrator-Only*: the main agent NEVER writes code — it only delegates.
2. *Aggressive Parallelism*: decompose into the smallest independent parallel units.
3. *Fan-Out Validation*: review runs as a scalable roster of independent lenses,
   not a single pass (see =skills/phases/post-merge-review/SKILL.md=).
4. *Zero Tolerance*: every validation gate must pass on verified findings.

** Parallel Execution Strategy

*** Implementation Phase
- Up to 4 parallel executors per batch, grouped by file independence.
- Interface/stub batch first, then implementations, then tests.

#+begin_src
Batch 1 (parallel):  interfaces/types · core service A · core service B · controller stubs
Batch 2 (parallel, depends on 1):  service impls · repository impls · controller impls · middleware
Batch 3 (parallel, depends on 2):  unit tests A · unit tests B · integration tests · e2e tests
#+end_src

*** Fan-Out Review Validation

Review is not a fixed set of three architects. The supervisor invokes the
**fan-out review engine** (=skills/phases/post-merge-review/SKILL.md=), which:

1. Spawns a roster of independent review *lenses* (core: correctness, security,
   code-quality; extended lenses added by change profile + remaining quota).
2. Has each lens report *every* candidate finding (coverage; no self-filtering,
   no per-lens verdict) in the =[ISSUE-N]= format.
3. Loops until dry (K consecutive rounds with nothing new), then adversarially
   verifies each fresh finding with ≥3 independent skeptics (majority-to-confirm).
4. Routes any confirmed finding to an executor fix and re-runs the whole gate (a
   fixed point), passing only on a clean, fully-verified cycle.

The number of lenses (N) and verifiers (V) scale with the change and with quota;
the zero-tolerance bar does not.

** Retry / Fix Cycle

Handled by the fan-out engine's fixed-point loop: confirmed findings → executor
fix → entire gate re-runs. If =MAX_FIX_CYCLES= (=max_code_review_iterations=) is
exhausted with findings still confirmed, the engine pauses and surfaces them to
the user — it never auto-passes.

** Rate-Limit Handling

Swarm supervisors follow the same protocol as every workflow. See
=skills/shared/rate-limit-handling.md=. After every parallel batch (executors,
review lenses, or verifiers), run =detectRateLimit()= on each agent's output. If
any reports a marker:

1. Capture partial results from agents that *did* return — don't discard work.
2. =applyRateLimitPause(state, { reason, resumesAt, workflowPhase })= with the
   current phase (=implementation=, =validation=, =quality_gate=).
3. Schedule =CronCreate= with =buildResumePrompt(workflow_id)= and
   =buildCronExpression(resumesAt, { timezone: 'utc' })=.
4. Print =buildPauseReport(...)= and exit the supervisor turn.

On =/workflow:resume=, the resume skill clears the pause and re-enters at the
recorded phase, picking up only the units that did not complete.

** Swarm vs Epic

| Feature                   | swarm                  | epic                          |
|---------------------------+------------------------+-------------------------------|
| Worktrees                 | single                 | one per component             |
| Decomposition             | parallel units in-tree | components + dependency waves |
| PRs                       | one                    | one per component + integration |
| Review                    | fan-out engine         | fan-out engine (per component + post-merge) |
| Used when                 | self-contained change  | independent multi-component scope |

** Best For

- Large feature implementations and multi-file refactors
- Critical production code where verified quality matters
- Any self-contained change that benefits from parallel execution

For independent multi-component scope (e.g. "build a full application with X, Y,
Z"), the architect selects epic execution instead.

** Agent Teams Enhancement (Experimental)

When =CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1= is set, swarm can use Claude Code's
native Agent Teams for peer-to-peer coordination instead of the =Task= tool.

| Workflow concept   | Agent Teams equivalent   |
|--------------------+--------------------------|
| Supervisor         | Lead agent (delegate)    |
| Executor           | Teammate                 |
| Review lens / verifier | Parallel teammates   |
| Aggregator         | Shared task completion   |

If Agent Teams is unavailable, swarm falls back to the =Task= tool approach
automatically — no changes needed.
